# Redis 设计指引

## 一、基本概念

### 1.1 部署模式

| 模式 | 说明 |
|------|------|
| 单点模式 | 无高可用能力，数据仅存在于一台 Redis 节点上 |
| 主从模式 | 通过增加从节点实现数据高可用，数据定时由主节点同步至从节点，主节点异常时需手动切换 |
| 哨兵模式 | 在主从模式基础上增加哨兵节点，主节点异常时自动切换主从关系 |
| 集群模式 | 在主从模式基础上增加数据分片能力，每个分片通过主从模式实现高可用，自动识别节点状态并切换 |

### 1.2 持久化模式

| 模式 | 说明 |
|------|------|
| 内存模式（默认） | 数据仅存储于内存，无持久化；性能最佳、数据可靠性差、故障恢复简单快速 |
| RDB 模式 | 数据存于内存，同时定时持久化全量数据至硬盘；性能较好、可靠性较好、恢复时间较长 |
| AOF 模式 | 数据存于内存，同时每秒持久化增量数据至硬盘；性能最差、可靠性最佳、恢复时间较长 |

### 1.3 缓存数据结构

| 数据类型 | 说明 |
|---------|------|
| 字符串（String） | 存储字符串值，也可存储文本、整数或二进制数据；常用于缓存、计数器、分布式锁等 |
| 哈希（Hash） | 存储键值对集合；常用于存储对象属性、配置等 |
| 列表（List） | 存储有序字符串队列，支持头部和尾部操作；常用于动态数据等 |
| 集合（Set） | 存储唯一字符串集合，支持交并差操作；常用于唯一标识、用户关联等 |
| 有序集合（SortedSet） | 每个元素关联分数，支持排序和范围查询；常用于优先队列等 |
| 位图（Bitmap） | 存储位操作数据，支持位设置、清除、统计等；常用于用户统计等 |

### 1.4 缓存数据淘汰策略

| 策略 | 说明 |
|------|------|
| Noeviction（默认） | 不淘汰数据，内存达上限时拒绝写入并返回错误，只响应读操作 |
| volatile-lru | 对设置了过期时间的键值使用 LRU 算法剔除 |
| allkeys-lru | 对所有键值使用 LRU 算法剔除 |
| volatile-ttl | 根据 TTL 属性剔除即将过期的键值 |
| volatile-random | 随机剔除设置了过期时间的键值 |
| allkeys-random | 随机剔除所有键值 |
| volatile-lfu | 对设置了过期时间的键值使用 LFU 算法剔除 |
| allkeys-lfu | 对所有键值使用 LFU 算法剔除 |

## 二、服务特点与模式

### 2.1 服务特点

- **多模式支持**：支持主从模式、集群模式
- **信创适配**：支持鲲鹏、海光芯片、麒麟操作系统
- **局部故障自愈**：服务器宕机等异常场景时自动恢复、重启
- **高可用切换**：主从/集群模式下自动进行主从切换

### 2.2 服务模式选型

**缓存服务主从模式**
- 默认配置：1主1从 + 3哨兵节点
- 推荐场景：小规模应用（TPS < 20000 且 存储数据量 < 10G）
- 路由机制：VIP 路由，客户端配置单个 VIP 地址
- 规格选型：
  - 低配版：1C/4G，存储上限 2G
  - 标准版：2C/8G，存储上限 4G
  - 高配版：4C/20G，存储上限 10G

**缓存服务集群模式**
- 默认配置：3分片，每分片1主1从
- 推荐场景：大规模数据存储或高并发（TPS > 20000 或 存储数据量 > 10G）
- 分片数量：分片数 = 2n+1，n≥1，单分片存储 ≤ 10G
- 规格选型：
  - 标准版：4C/8G（3分片），单分片存储上限 4G
  - 高配版：4C/20G（3分片），单分片存储上限 10G

### 2.3 可用性分析

| 维度 | 主从模式 | 集群模式 |
|------|---------|---------|
| 高可用 | 数据多副本，服务端高可用 | 数据多副本+分片存储，服务端高可用 |
| 数据复制 | 主从复制存在时延，仅支持最终一致 | 同左 |
| 主节点故障恢复 | 分钟级 | 秒级（取决于客户端拓扑刷新周期） |
| 全量故障恢复 | 自动触发节点重建，20分钟内 | 超一半分片异常时触发重建，20分钟内 |

### 2.4 持久化选型建议

| 方案 | 适用场景 | 特点 |
|------|---------|------|
| Redis 内存模式 | 缓存非重要数据且接口为非核心接口 | 性能最佳，极端情况数据可能丢失 |
| Redis 持久化存储 | 需要数据持久化的业务 | 性能较好，可靠性较好，仅支持手动漂移 |
| 内存模式 + 数据库多级存储 | 核心交易类接口 | 兼顾可靠性和自愈能力，数据丢失时可访问数据库重新加载 |

## 三、设计指引

### 3.1 缓存依赖设计

> 缓存组件作为性能提升的辅助手段，关键交易接口不宜强依赖缓存服务。

**缓存接口熔断**：当访问缓存数据失效或不可用时，熔断接口。

**数据多级存储**：数据存储至缓存和数据库，当缓存失效或不可用时，降级访问数据库。

### 3.2 数据隔离规则

接入系统应在本系统范围内使用缓存服务，不宜多个系统混用。推荐按以下维度拆分：

- **按数据安全等级**拆分，存储至多套缓存服务
- **按数据业务领域**拆分（如按微服务领域），存储至多套缓存服务
- **按数据可用性等级**拆分（如管理类与业务类分离），存储至多套缓存服务
- **按数据访问频率**拆分，实现冷热数据隔离

### 3.3 部署区域原则

- 接入系统与缓存服务推荐部署至相同网络安全域
- 灾备、双活架构系统，应使用相同架构、规格的缓存服务
- 缓存服务访问地址不能发布至公网

### 3.4 功能接口设计

**数据淘汰**
- 缓存数据应显式设置合理的 TTL，避免雪崩
- 明确服务端 maxmemory-policy 配置，不使用默认值时应在申请时说明

**热点数据**
- 高频访问接口推荐设计数据预热、多级缓存等机制
- 设计数据库加锁、布隆过滤器等方案避免缓存击穿

**通知机制**
- 异步通知场景避免循环查询，推荐通过 Pub/Sub 命令实现
- 键值类操作推荐使用 keyspace-notification 机制，需评估额外性能开销

**数据一致性**
- 使用多级存储时，应设计缓存与数据库的读写策略、一致性更新、并发控制、重试机制、缓存失效策略等

### 3.5 缓存数据结构规范

- 业务 Key 不宜使用特殊字符（空格、换行符、双引号及转义字符）
- 业务 Key 推荐通过系统编号、模块区分，如 `J036X0:order:Key1`
- **不宜使用大 Key**：
  - String 对象：建议控制在 10KB 以内
  - 集合对象（hash、list、set、zset）：建议控制在 5000 项以内，超过应均匀拆分
- 推荐选择合适的数据压缩算法（JSON、XML、binary-data 压缩后存入）
- 非 Lua 场景下不宜使用 hashtag，避免出现流量倾斜

### 3.6 容灾功能设计

**设计方案**
- 缓存服务机房独立部署、数据不同步，接入系统缓存数据单元化改造
- 缓存服务同城机房双向同步，支持手动/自动容灾切换

**功能选型**

| 功能 | 选项 | 说明 |
|------|------|------|
| 数据同步 | 无需同步 | 热点缓存类数据优先使用单元化设计 |
| | 单向同步 | 主机房同步至容灾机房，切换后需运维反转同步关系 |
| | 双向同步 | 双向同步，解决数据回环和逻辑时钟问题，不支持数据双写 |
| 流量路由 | Proxy 容灾切换 | 通过 Proxy 隔离故障缓存，将请求路由至容灾机房 |
| | DNS 容灾切换 | DNS 将域名解析至容灾机房缓存服务 |
| 容灾切换 | 手动切换 | 通过手动操作执行 |
| | 自动切换 | 配置健康检查，失败时自动执行切换 |
| 读写策略 | 主机房读写 | 主机房承载所有请求，容灾机房热备 |
| | 读写分离 | 主机房承载写请求，容灾机房承载本机房读请求 |

**功能限制**
- Proxy 自动容灾切换不能处理网络分区，分区时降级为两套独立缓存
- 读写分离存在毫秒级同步时延，写入后可能读取不到，需通过重试规避
- 使用 Proxy 组件时，不支持事务和 keys 命令
